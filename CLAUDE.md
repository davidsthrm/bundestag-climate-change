# Part 1: Coding guidelines

**Tradeoff:** These guidelines bias toward caution over speed. For trivial tasks, use judgment.

## 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

## 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

## 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:
- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.

When your changes create orphans:
- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

## 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:
```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

# Part 2: Project rules

## Project
Student project for a university NLP module (paper + presentation, team of two).
Working title: Heat Without Debate? Parliamentary Attention to Climate Change in the German Bundestag
Monthly comparison (2004 to today) of climate attention and stance in Bundestag speeches with the
physical climate signal and public attention. Research question and hypotheses: only in
[README.md](README.md#research-question) (single source, do not copy them).

## Working rules
- Do NOT edit files, download data, install packages or run git commands (commit, branch, push)
  on your own. Explain what you want to do and why, show the proposed change, act only when asked.
- Read-only actions (reading files, inspecting data in `data/`, checks that write nothing) are fine.
- No personal names (lecturer, students) anywhere in the repo.
- One branch per task, merged into `main` via pull request. Raw data is never committed.
- Never merge a PR. Every PR is reviewed by the other team member; the author merges after approval.
- A decision is recorded only after both agreed in an issue or PR, with that link.
- Settings (time window, keywords, URLs) live in `config/`, not hard-coded in scripts.
- Every download is logged in `data/raw/MANIFEST.csv` (URL, access time, SHA-256).

## Context index
Read only the files the task needs.

| When you work on | Read |
|---|---|
| Research question, hypotheses, pipeline, setup | [README.md](README.md) |
| Anything that touches an agreed choice | [docs/context/decisions.md](docs/context/decisions.md); ideas not agreed yet: [extensions.md](docs/context/extensions.md) |
| Data sources, files, schemas, quirks | [docs/context/data.md](docs/context/data.md), `config/sources.yaml` |
| Relevance, stance, time series | [docs/context/methods.md](docs/context/methods.md), `config/settings.yaml` |
| Annotation | [annotation/README.md](annotation/README.md) |
| Paper, slides, grading, dates | [docs/context/paper.md](docs/context/paper.md) |
| Figures, tables, key numbers | `results/<phase>/README.md` of the matching phase |

## Keeping context current
- A PR that changes a decision, data file, schema or method also updates the matching context file.
- Key numbers for the paper go into the README of the matching `results/` phase.

## Results
- Scripts write figures and tables to `results/<phase>/figures/` and `results/<phase>/tables/`
  (phases: `2_data_understanding`, `3_data_preparation`, `4_modeling`, `5_evaluation`).
- Files are generated by code, never hand-edited, and named with the script prefix
  (e.g. `02_precision_by_period.csv`).
- Phase 1 lives in `README.md`, phase 6 in `paper/` and `slides/`; `viz/` is a helper for data understanding.

## Subagents
- Delegate searching, bulk reading, data inspection and mechanical checks to the agents in
  `.claude/agents/`. Method choices, statistics, paper text and final answers stay with the main agent.
- Before using a subagent's result, check it against the source (spot-check the file, line or
  number it cites).
- Subagents never edit files or run git.
- Repeated procedures are skills in `.claude/skills/` (`/open-pr`, `/new-issue`); `.claude/settings.json`
  blocks edits under `data/` and merging.
